# F10 initial bound Owner recovery: draft contract

Goal: recover an authenticated incarnation-1 Owner and its original FirstHost after both are kernel-observed exited, while no Applied has ever committed and the initial recovery ledger may not have been initialized. Preserve original ready FIFO, zero attempts/segments, all budgets, process ownership, signatures and UNKNOWN refusal. This is distinct from the accepted schema28 successor bound-abandonment path.

Current facts: coordinator owner_resume.go only routes Applied0 + nonempty succession authorization to bound abandonment. Inc1 instead opens an existing recovery lease and fails if the ledger/lock/directories are absent. Submit placed initial tasks in ready/queued dependency states with assigned ready_sequence. Owner Bind does not Claim; activation and signed Applied are prerequisites to ClaimReady. Initial Owner runtime binds and relays FD4 before opening runtime directories and its recovery ledger.

Proposed narrow authority:

1. Current owner must be incarnation1, bound, control revision1, Applied revision0, original FirstHost still current, no historical applied_hash, valid Coordinator-signed binding and permit. Both exact PID/birth tuples must be Exited, never UNKNOWN. Current origin must remain alive and identical; executable/hash/generation must remain pinned. Scope is the existing launch; no origin-rebind support is added here.
2. Entire launch/run must have no attempts, segments, execution reservations, pending stops or questions. Every task must retain its original ready/queued state, work revision and ready sequence. Save a deterministic bounded queue snapshot hash/count in an immutable proof. Recovery does not call takeReadySequence, queueResume or create an attempt.
3. Add schema29 immutable initial-abandonment proof, separately accounted from schema28. Do not fabricate predecessor/inbound authorization or relax schema28 Applied guards. A nullable initial-proof reference on succession authorization identifies the initial-ready queue mode and carries it through later never-Applied successors. Existing ordinary authorization uses resume_queued as before.
4. Filesystem initialization is a distinct private Coordinator-only path. Validate/pin canonical state and private owner directories via held FDs. Existing files must match the original owner scope, canonical bytes and immutable authority; foreign, damaged or nonzero/pending recovery states fail closed. Absence can authorize only an initial zero-attempt record, never reset an existing record. Hold the same original directory/lock lease across Store proof preparation, exclusive ledger publication, revalidation and final retirement/authorization. Detailed crash publication stages and exact facts remain to be reviewed before implementation.
5. Prepare proof+queue snapshot+file facts and quota in one owned DB transaction. Publish the zero-state original-scope ledger using exclusive atomic creation; replay an existing exact publication read-only. Then mark proof applied and create the one adjacent successor authorization/retire inc1/offline the original Host atomically. Successor inc2 follows existing signed recovery handoff on the now-existing ledger. Preserve budgets and all ready sequences. Same command replays one authorization; a different command cannot reset or double-publish.
6. For later successors that remain never Applied, schema28 must preserve the initial-ready marker and original snapshot; it may transfer only existing scope, not initialize again. Fully Applied Owner paths retain their current contracts.

Main unresolved details: how existing zero-state vs absent lock/ledger pins enter immutable Store facts, exact queue snapshot bound/quota, and all schema trigger branches that must preserve initial-ready mode.

Minimum evidence once design is stable: focused Store initial queue/no-attempt/command-replay guards and actual deferred-FK cleanup; file crash stages for absence/prepared/publication with foreign/damaged/nonzero refusal; one real authenticated public CLI initial Bind-only death -> inc2 production execution/accept, with original Owner/Host Wait and unchanged FIFO/budget. ## Filesystem authority and crash contract under review

Store already captures canonical state root and database device/inode at Open in configIdentity/configStoreNodes and validates it after migration. Reuse this existing private DB-bound root identity to mint a non-forgeable StoreRootAuthority during Resolve; revalidate current root/database identities at Resolve, Prepare and Finalize. Neither the instance lock file, in-memory Owner key nor registration mutex proves that the current state pathname still refers to the database authority.

Proposed Coordinator-only OpenInitialOwnerRecoveryPublication receives StoreRootAuthority, exact scope/owner and optional prepared proof. Before mkdir or opening a new lock, open the canonical state root O_DIRECTORY|O_NOFOLLOW and state.db relative to the held root, verify expected device/inode, UID/private modes (0700/0600) and database single link. Hold root/database/spool/launch/lock FDs and flock throughout publication. Only before a proof exists may missing inert private directories/lock be created under this pinned root. A prepared proof requires all recorded directory/lock identities to remain; missing pieces fail closed and must not be recreated.

Absent ledger and exact canonical version2 zero ledger are the only admissible forms: matching scope/authority, no attempts, next sequence zero, not unavailable, no reservation/pending handoff. An existing canonical zero ledger is reused read-only. Prepare allocates both proof and final authorization quota so filesystem publication cannot be followed by an avoidable quota failure. Immutable proof fields and a monotonic prepared→finalized phase may share one table; same-command replay resolves first, a different command conflicts.

Prepare records one unpredictable stage name (derived from its immutable authorization ID) and the exact canonical zero bytes hash. Every retry uses only that proof-bound name; no fresh stage is allocated per retry. Unknown stage names are neither read nor deleted. Ordinary overwrite-capable persistBytesRenameat is unsuitable. Under the held lock, exclusively create that named stage or reopen its existing private regular single-link file. A prior interrupted stage must be a byte-for-byte prefix of the intended canonical zero bytes, at most their exact length; append only the missing suffix after rechecking the held/named inode. Reject all other contents, never truncate or unlink foreign bytes. Check all short writes, reread/hash the full staged bytes, fsync the stage FD, perform no-replace rename, verify published inode/bytes, then fsync the directory. This permits partial-write crash replay with at most one bounded stage for a proof. After publication but before directory fsync, replay may see absence (retry publication) or exactly the prepared canonical zero ledger (reuse); any other bytes/identity fail closed. Reobserve exact typed deaths and the DB/FS snapshot before atomic Finalize creates authorization and retires/offlines the old actors. No filesystem IO is performed inside a SQLite write transaction. Root replacement at any stage must reject before touching the replacement; held FDs may only reference the old root.

The proof snapshot mutation fence is not decided yet. A broad freeze of every control API was suggested, but actual initial-ready reachability of Rework/SubmitPlan/BudgetRevision/Stop is being checked first. Initial recovery response must truthfully represent initial_ready, including command replay and later bound-never-Applied successor propagation; existing fully-Applied receipt and resume_queued paths remain unchanged.


## Reachable mutation audit and proposed minimal fence

Read-only source audit corrected the broad initial proposal: existing-run SubmitPlan fails its INSERT conflict; both Rework routes require terminal task/segment history absent in this shape. They do not need new fences. Ready/queued RequestStop is reachable and cancels the anchor plus blocks dependent tasks; policy-backed ReviseBudget is reachable before any Claim, scoped strictly by run+group. Execution policy records are immutable.

The durable fence covers only the target run's Stop and new BudgetRevision writes. Stop has no command receipt: check it in the shared requestStopTx after resolving task run/work revision and before task writes, so ProviderControl disable's enclosing transaction also rolls back its earlier provider-setting write. BudgetRevision checks the fence after authenticated existing receipt replay and before CAS/insert. Prepare inserts the immutable proof and fence in one transaction. The proof has monotonic prepared→finalized→activated phase: finalized means FS publication plus successor authorization/retirement committed; activated is set in the first successfully committed signed Applied of a successor carrying initial_proof_id. Keep Stop and new BudgetRevision refused with an explicit owner_initial_recovery_pending conflict until activated. This prevents legal drift not only between Prepare/Finalize but also between authorization and the first Applied, including later never-Applied successors. Replayed pre-existing budget commands remain readable; unrelated runs are unaffected. ClaimReady is already blocked before Applied; the first Applied and fence release share a transaction. No attempt/budget/queue is created merely by recovery.

The exact initial snapshot is <=64 tasks sorted by task ID, including all scheduling state/payload/policy/effective-budget inputs previously listed, excluding presentation-only timestamps. Proof has immutable reserved_authorization_bytes covering the frozen authorization and retirement-row growth. A schema trigger includes this durable escrow in both run/global storage_usage while prepared. Finalize exchanges escrow for actual authorization and retirement growth in the same transaction (actual increment must be <=reserved), releasing any unused portion; rollback restores the reservation. The fixed proof overhead conservatively includes the longest phase name. This is not merely a transient storageAdmission check. Physical free disk remains rechecked and can still fail if an external writer fills the filesystem; durable logical quota does not promise physical preallocation. Proof+escrow storage is charged before FS publication; the authorization FK is nullable for ordinary paths and immutable for initial paths. Once activated, subsequent ordinary fully-Applied resume does not inherit initial_ready semantics. Public initial receipt mode/status are initial_ready, CLI takes the same successor launch branch as successor mode, and replay preserves that choice. Later never-Applied successor receipts also use initial_ready until activation.

This fence is a recovery-in-progress contract, not a global plan lock. Origin loss/rebind while authorization is pending remains separately unimplemented; no origin-rebind support is claimed. Physical directory/database replacement still fails closed. Final independent design review is required before production edits, without another user approval gate.


StoreRootAuthority is an exported Store type with only unexported fields and no public constructor, minted solely by the authenticated Resolve path against the original Open identity and saved proof. Host may import Store (already an existing dependency), hold this value together with root/database FDs, and query a copied node fingerprint for exact matching; only Store can mint a nonzero authority. Validation reads immutable Open identity and current nofollow root/database nodes. Finalize checks the authority immediately before and after its transaction commit. A post-commit mismatch returns owner_initial_recovery_uncertain with no successor launch; the already committed proof/authorization is not rolled back or reminted. Initial-proof successor admission must validate the same saved root/database authority before CheckRecoveryAllowed or any other state-path/key access, including receipt replay -> public successor launch. Restart/copy into another root fails the saved proof pin. Ordinary receipt replay stays immutable, but cannot bypass the admission root check.
