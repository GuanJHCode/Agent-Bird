# Host launch bootstrap publication lease

Scope: same frozen candidate's native/local rebind writers and recover-host; preserve all Store schema30 receipt/authentication/UNKNOWN/Wait rules. Different executable versions or direct external IPC writers are not claimed to participate. No new database schema or execution authority.

A per-launch lease under existing state/host-recovery/<sha256(launchID)>.lock covers bootstrap read, one bounded Rebind RPC, validated response, FD-relative atomic publication, fsync and namespace postcheck. Busy/cancel before acquisition never invokes RPC. RPC uncertainty never publishes. After committed RPC and filesystem failure, existing authenticated exact replay repairs publication. No automatic retry/rebinding is added.

Canonical V2 bootstrap path must be resolvedState/host-bootstrap/<launchID>.json (one safe path component). Hold original state, host-recovery and host-bootstrap directory FDs; root/recovery remain0700. Bootstrap directory allows only0700 or0500 (same owner;0500 permits reading an existing recovery file and preserves real post-RPC write-failure replay). Lock and bootstrap must be regular0600 single-link same-owner. All directory/lock named identities are rechecked before RPC, before/after publication. Bootstrap snapshot also keeps exact bytes and file identity through publication; unexpected external edits fail closed rather than overwritten. Paths with private-file alias/symlink/hardlink or cross-state metadata fail before RPC. Publication uses openat/no-follow temp0600, write+fsync, renameat in held FD, directory sync. Only own temp is removed on pre-rename failure; no previous file or lock is unlinked.

Use bounded5s cancellable flock and bounded5s Rebind child context; no worker budget changes. Readers may see the complete old/new snapshot and Store rejects stale identity. recover-host uses the same lease before reading, retains the existing startup-intent name and no-repeat-spawn behavior. Initial exclusive bootstrap creation still precedes control capability publication.

Validation: one deterministic two-child CLI ordering regression with a delayed fake RPC response (real flock, original Wait); a targeted root/directory replacement check; existing real pending-auth public fault/replay verifies actual DB plus filesystem/receipt lifecycle. Reuse schema30 Store/race/Linux evidence; only affected CLI/FS evidence rerun. Independent review before merge. These prove cooperative writer ordering and fail-closed publication, not atomic DB+FS transactions or safety against malicious same-UID ABA.
