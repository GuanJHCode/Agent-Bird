## Durable lifecycle and accounting

Schema11 adds object registry, uploads and pins. Begin durably reserves all initial objects before the first staging file; each object reserves expected_size+4096 and each upload reserves4096 metadata. Upload metadata is bounded4096. Staging, published-but-uncommitted objects and abandoned/deleting files remain charged. Upload tombstones remain charged after successful GC for stable idempotence.

Coordinator is sole writer; each bounded chunk holds mutex and a short DB transaction, no writer FD survives RPC. An uncommitted partial chunk is compared byte-for-byte before completing its prefix; unknown existing staging inode is never adopted or deleted. Publish is exclusive link, file/directory fsync, remove staging link and directory fsync; known one/two-link crash states recover by recorded identity. Parent directory is synced on root creation. No overwrite or mtime-based deletion.

After publication, a short transaction rechecks source/current owner snapshot/availability/capability, validates every full body and final input budget, pins all refs, stores the small exact decision and adapter, advances revision/ready sequence and revokes old report capability atomically. Only then scheduling is possible. Commit reply loss returns exact saved receipt.

Explicit exact abort removes writer/recovery eligibility. GC accepts only abandoned/deleting known objects with no pins/active recovery, verifies durable device/inode, unlinks known files, fsyncs directory then deletes registry and releases object charges. Failed deletion/identity mismatch retains accounting. Old aborted upload GC cannot delete a brief reused by a newer active upload. Unknown orphan identity stays charged and requires explicit resolution; no guessed cleanup.

## R5 final protocol and verified repair (supersedes r4 GC)

Independent r4 review proved that a validated mutable source filename could be replaced before unlink: its foreign inode was deleted even though the held-original FD prevented quota release. Evidence review-r4/late-path-replacement.json and overlay are unchanged. After root confirmed every r4 reviewer test session ended, root explicitly handed back sole writer responsibility. Permanent normal-r5-path-red.json reproduced file/symlink deletion against unchanged r4 product code (3 fail events including parent,1 directory subtest pass), then the product fix was applied. No tests ran concurrently with source writes in this r5 turn.

R5 preserves r4 complete known-link preflight and held-original FD. After successful preflight with actual names, GC creates one random0700 `.gc-<uploadID>-<nonce>` directory below the already trusted object root, holds its directory FD and an os.Root capability, and atomically captures each mutable source entry using Darwin RenameatxNp(RENAME_EXCL) into that private namespace. Source and quarantine directories are synced. The captured entry is then checked for complete registered dev/inode,regular type,uid,0600 and expected remaining nlink. Only a proven captured object is unlinked inside the private namespace. There is no check-then-unlink of the original mutable source name. Captured file identity is also checked through a held no-follow FD. Worker/request paths never expose this namespace. After all captured known links are removed, directory fsync plus original held-FD nlink0 remain prerequisites for registry DELETE and charge release.

A foreign file,symlink,directory,rename/fsync failure or crash after capture is preserved, not restored over an occupied source path. The object row stays charged deleting. Captured/ambiguous quarantine is externally visible as `rework_cleanup_quarantine_awaiting_cleanup_decision`. No automatic directory adoption,traversal,restoration,unknown unlink or cleanup is performed on retry. Atomic no-overwrite also prevents capture from overwriting a retained destination. A platform helper uses the already pinned x/sys0.31.0; non-Darwin checks return explicit unsupported before making a quarantine directory. No new schema,generic registry or dependency upgrade was introduced.

Creation/deletion intent: the existing durable deleting object row plus abandoned upload is committed before quarantine creation. The directory prefix binds its random name to that exact upload. The nonce is not durable inode authority: after a crash the prefix only acts as a conservative barrier, never permission to adopt or delete the directory. A missing recorded object inode remains charged when identity cannot be re-established, including capture/unlink-before-registry-commit crash states. This is deliberate conservative manual recovery, not automatic crash reclamation.

Bounded metadata and retention: existing root entry names are checked for the exact upload quarantine prefix without entering or adopting that entry. If an upload already has a barrier while objects remain, retry returns awaiting_cleanup_decision rather than creating another. Both objects in one normal GC share one private directory. Thus trusted GC retains at most one barrier per upload. A successfully emptied barrier is retained with the upload tombstone for precise retry/boundedness until an explicit owner retention/cleanup decision resolves that tombstone; no automatic TTL/pruner is implemented or claimed. Upload4096 remains charged as logical metadata overhead including this fixed additional entry, not an assertion about APFS allocation blocks. Successful `removed` means object bodies were removed; the optional v3 `cleanup_reason=upload_tombstone_and_quarantine_barrier_retained` explicitly distinguishes retained metadata from a fully cleaned runtime. Nonempty/unknown quarantine requires explicit owner cleanup decision. Production never clears an unknown barrier merely to enable a retry.
