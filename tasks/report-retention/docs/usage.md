# Managed report attachment retention

Schema 39 adds opt-in retention for managed `report` attachments (`result` and `failure`). Collection removes only the original managed object's `data.bin`. It retains report events, durable ACK metadata, intake descriptors, original proof and ownership, the deletion intent and physical marker. Provider source files are never collected.

A successful report needs the exact `handled` decision, a completed latest attempt, all original segments proved exited with settled budgets, no pending events/questions/intakes and no active resource pins. Retention is 30 days after the later trusted exit or consumption time. A failure additionally needs an explicit per-intake `resolved` or `abandoned` disposition with a reason; its seven-day retention starts at the latest of resolution, exit and consumption. The exact boundary remains retained. UNKNOWN does not become terminal through resolution.

All commands accept `--state-dir`, the original `--control-file`, and an absolute `--request` path to a regular owner-only `0600` JSON file. Use a task-owned `0700` directory. Requests and plans are bounded to 8191 JSON bytes. No request can set the clock or shorten the retention period.

- `report-artifact-retention-resolve`: `{"version":1,"run_id":"run","intake_id":"managed-intake-id","request_id":"resolution-1","resolution":"resolved","reason":"Failure addressed and recovery data no longer needed"}`. `intake_id` is the object identifier in the original managed attachment path `managed-artifacts/<intake_id>/data.bin`, returned with the report. A resolution is immutable and bound to the current owner/rebind identity; repeat the exact request for its original receipt.
- `report-artifact-retention-plan`: `{"version":1,"run_id":"run","request_id":"retention-1","limit":8}`; add `after_intake_id` from `next_after_intake_id` to continue. A page scans at most 64 intakes. Output includes eligible references, counted exclusion reasons, owner binding and a plan digest. Planning does not remove content.
- `report-artifact-retention-apply`: pass the exact saved plan object as the request file. It rechecks owner, physical identities, consumption, terminal evidence and pins. A crash after removal leaves a durable prepared intent, and replaying that same plan completes it. Exact old report ACK replay never rebuilds removed bytes.
- `report-gc-status`, `report-gc-enable`, `report-gc-disable`: `{"version":1,"run_id":"run","expected_revision":0}`. Status is read-only. Enable and disable compare the current revision and increment it. Initial status is disabled/revision 0. Policy retains a token hash, never the token. Owner/rebind drift stops automatic work. After an explicit disable, the same owner binding can enable a new revision to resume the exact pending plan; a changed binding cannot adopt that pending plan.

Automatic collection shares the Coordinator's wake, cancellation and idle fence. Each round visits at most eight run policies, each with at most 64 scanned intakes and eight removals. An unfinished exact plan is retained for recovery; uncertainty never releases the raw-byte reservation. Marker and index metadata are charged before physical deletion and remain charged afterwards.

Store consumer integrations can acquire/release `PinReportArtifact` with an owner, reason and release condition before using a report body. Pins cannot be acquired once deletion starts. Existing report consumers are protected by delivery and terminal guards; report events are not accepted as candidate inputs.

Scope excludes Host terminal/progress artifacts, Git worktrees/private refs, provider source directories and process recovery records. This is not a native Provider/TUI acceptance claim. No existing user runtime has been opted in or deleted during implementation.
