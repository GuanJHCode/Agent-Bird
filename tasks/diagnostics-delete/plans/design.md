# F02 explicit completed-attempt diagnostics deletion (frozen contract)

Scope: owner-authorized explicit deletion of managed detailed diagnostics for a completed task, with no active/unknown segment and no reading/pending diagnostic page. Not automatic TTL/GC, report/candidate artifact deletion, legacy_pending adoption, failed/unresolved execution, physical2GiB or overallF02 completion. Default retention is unchanged; a specific authenticated delete request is an explicit owner disposal decision. No live user data is touched by implementation/fixtures.

## Public and Store contract

Add diagnostics-delete request Version1, TaskID, AttemptID, RequestID, ExpectedRevision, plus existing control-file authority in CLI. No user-supplied path or quota amount. Reuse diagnostics token/JSON limits and original run/controller/token/task/attempt/producer/policy/reservation authorization. One immutable command per reservation, and a run/request ID cannot name a second command. Exact retries retain original plan and completion bytes; changed arguments conflict. Reads after deleting fail unavailable; after released fail expired. Existing ACK never starts deletion or frees bytes.

Admission requires task.status=completed (the current accepted completion contract), a bounded set of original attempt segments all runtime/segment exited, no current/resumable execution or UNKNOWN, diagnostic phase=idle and exact next_revision, and the same reserved/active diagnostics reservation. This is intentionally narrower than deleting a failed/paused attempt; rework creates another attempt and cannot reclaim this namespace. Completed is the existing task completion contract (including existing fixture/artifact policies); diagnostics is not a candidate/report input, so ordinary delivery ACK/pins need not be empty. This gate is checked twice before fresh preparation and frozen in the intent; exact prepared retries/finalization use original attempt/segment facts, not today's task status/revision, because an authorized rework may already have advanced the task.

Use schema31 diagnostic_deletions: immutable original identity/request, saved Store root nodes, canonical physical plan, completion template, physical tombstone bytes, and phase prepared->removed. No migration backfill/adoption; upgrading schema30 rejects any pre-existing diagnostics deleting/released reservation as orphan state, without changing the old database. Schema31 enforces a full diagnostics-only state allowlist: unchanged state, reserved->active, reserved/active->deleting with exact prepared intent, deleting->released with exact removed intent and idle delivery; every other transition (including reserved/active->released) is rejected. Inserting a diagnostics reservation starts only reserved; legacy_pending is not adopted. prepared->removed requires the matching reservation already deleting and delivery idle. Schema31 enforces the cross-table transition: a diagnostics reservation may enter deleting only with its exact prepared intent; deleting->released requires that same intent phase=removed and idle delivery; deleting/released cannot regress. Deletion identity/plan/template/cost are immutable and its only phase transition is prepared->removed. Reservation deleting/released forbids all diagnostic delivery advancement. Inserts start only in prepared with exact original reserved/active reservation and idle delivery. Guards apply only to class=diagnostics, preserving other artifact classes. Removed phase and reservation release happen in one final transaction. All TEXT/BLOB UTF8 lengths plus fixed integer costs and the retained physical tombstone bytes are control-accounted at prepare; completion template is charged upfront. Reservation state reserved/active->deleting in the same transaction as intent; it remains counted at the full reserved maximum through all uncertainty. Only confirmed filesystem deletion followed by the final transaction changes deleting->released. Metadata/tombstone remain accounted. Return released reservation bytes separately from removed logical file bytes; do not claim filesystem blocks or physical disk reclamation.

Flow: authenticate read-only snapshot -> acquire existing filesystem writer/update locks and capture exact closed namespace plan -> new same-connection Store transaction re-authenticates terminal state/phase/revision/reservation/root, charges and persists intent, CAS deleting -> commit/postcheck -> filesystem deletion -> final Store transaction validates exact intent/root and held physical proof, marks removed/releases reservation once -> exact response. No Store mutex/SQL transaction spans filesystem reads/unlink/fsync; namespace locks may span the short Store transactions. Concurrent read wins its reading fence or delete wins deleting CAS, never both. Concurrent deletion is serialized by existing namespace locks. First commit error performs no deletion. Final commit error leaves a replayable deleting intent; quota remains retained unless the actual commit succeeded. Use audited ownerTransaction physical rollback/discard and new private beginRootedOwnerTransaction: acquire sql.Conn first, validate StoreRootAuthority against saved Open identity, BeginTx on that connection, commit with root postcheck. Never call beginInitialOwnerTransaction with a synthetic initial selector or export root authority construction. Existing initial-owner protocol remains unchanged.

## Historical proof compatibility

DiagnosticsGrant is also in historical candidate launch hashes. Split the internal binder into live execution and historical-proof modes, carried explicitly from candidateArtifactUse and dag_rework_evidence. Live ClaimReady/PendingLaunches accepts only reserved/active. Historical proof may reconstruct the ORIGINAL immutable DiagnosticsGrant for deleting/prepared or released/removed only with an exact matching deletion identity, request/plan, policy/namespace/reservation facts; this copy is only for verifying old intent hashes and cannot be dispatched or returned in Host IPC. This allows legitimate DAG rework after deletion and avoids treating retired bytes as new execution authority. Existing valid reserved/active historical proofs keep their behavior. Add one regression demonstrating historical rework proof succeeds while the same retired segment cannot be live-dispatched.

## Filesystem contract and frozen interface

Managed root is derived from saved Store state/host-spool/producer/attempt/.diagnostics and exact Scope.Hash. Never create a missing namespace, writer lock or update lock. Take writer EX then update EX, matching current Writer lock order, with bounded/cancellable acquisition; verify canonical path/no symlinks,0700 directories,0600 same-owner single-link files, held/named inode identities. Initial plan requires a valid exact-scope manifest Closed=true, no Pending/unclean stage, and complete bounded slot hashes. No active writer can prepare a plan. Use one reusable ChunkBytes buffer (20MiB data is not collected in memory).

Frozen internal diagnostics API: `OpenDeletion(ctx context.Context, root string, scope Scope, commandID string, savedPlan []byte) (*DeletionLease,error)`; `Plan() []byte` returns a defensive copy of canonical bounded immutable bytes (maximum 64 KiB); `MarkerBytes() int64` returns exact retained permanent metadata cost; `RemovedBytes() int64` returns original planned logical data-file lengths; `Remove(ctx context.Context) error` performs resumable removal; `VerifyRemoved(ctx context.Context) error` checks marker and absent original files while retaining locks; `Close() error` releases FDs. No exported mutable proof fields. Store constructs and charges an immutable completion response from the authenticated intent and those getters at prepare, and returns it only after `VerifyRemoved` plus final rooted transaction. savedPlan comes only from authenticated DB, never public input. Fresh OpenDeletion only inspects; Remove is called only after durable Store intent. Missing/tampered evidence fails closed.

Plan binds root/namespace/lock dev+ino+uid/mode plus each recognized data filename, inode identity, size/time and SHA256, scope, command ID and a frozen random stage basename. Maximum original inventory is fixed SlotCount+manifest/locks; unknown files, symlinks, hardlinks, changed content or namespace replacement reject. On replay keep the original plan; do not recompute/adopt replacement files or refund from current size.

Before unlinking anything, publish a private immutable deletion marker binding command/scope/plan hash: deterministic bounded body, unique frozen stage, file fsync, no-replace rename, directory fsync. Exact torn stage prefixes can recover only under the saved intent/private directory identity; conflicting marker/stage remains blocked. Marker makes ordinary Reader/OpenWriter reject the retired namespace (existing unknown-file fail-closed path is sufficient). No marker or durable intent means missing original files are not accepted as proof of authorized deletion.

Then unlink only the original planned data files using held-FD relative operations after identity+content checks; manifest is last. Replays accept missing planned files only under the exact marker. Verify inventory remains exact, fsync directory, retain marker plus original empty writer/update locks and namespace directory permanently as bounded accounted tombstone. Never unlink lock files, rmdir the namespace, recursively remove an unknown path or delete a recreated identical-byte/different-inode file. New files or partial errors retain intent/quota and remaining evidence. Store finalizes only after VerifyRemoved under the same held locks. This prevents a completed deletion from enabling an old signed writer to recreate the namespace.

## Validation / ownership

Freeze exact terminal gate, schema/cost and filesystem interface before parallel implementation. ROOT owns Store/schema/public IPC/CLI and integration. A separate isolated writer may own internal/diagnostics deletion implementation/tests after contract review; no shared-source worktree writing.

Minimal evidence: owner/phase/revision/UNKNOWN refusal without filesystem effects; actual closed managed data delete->expired read + exact command replay/quota once; concurrent read/delete gate; actual COMMIT error before deletion and after FS removal; physical partial deletion reopen/replay plus inode/unknown-file and live-writer refusal. Prefer small grouped regressions and one existing public diagnostics flow extension; reuse existing capture/read/ACK/accounting and owner transaction tests. One controlled process crash exercises durable marker/partial-removal recovery if the implementation adds crash recovery claims. Mac/native Linux only; no real models/accounts/install changes/push.

Review resolutions: completed/work revision gates freeze only at initial prepare; same-command replay never requires the current task to remain completed. Historical-proof grants are internal and never executable. Schema31 triggers enforce deletion/delivery/reservation progression. Store root construction remains private and same-connection. Permanent metadata compaction, deletion of failed/uncertain namespaces, and same-UID deletion/ABA of tombstones are outside this batch. ROOT owns candidate_input.go historical-mode threading and dag_rework_evidence.go; the F03 worker may implement its isolated v2 compose branch in that file; ROOT owns resolving the small historical-mode hook at integration.
